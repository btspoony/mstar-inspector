# ADR: Split the GitHub App from the Review Bot and relay quota across an ordered bot chain
Status: implemented — `github_apps` carries the App's credentials, installations and publishing identity, `review_bots` carries the review configuration and its multiplier, and the two meet only in the per-install chain `app_install_bots`, walked in position order by `selectReviewBot`
Spec: docs/specs/feature/bot-scope-and-claiming.md § Current state
Supersedes: 2026-11-15-review-bot-and-target-entities.md — the `review_bots`-as-one-execution-and-configuration-row half only; the `review_targets` half stands
Supersedes: ../feature/2026-11-15-shared-bot-scope-and-claiming.md — the one-`scope`-answers-both question only

## Problem

One `review_bots` row was three things at once: a GitHub App's credentials, a review configuration, and one workspace's ownership of both. The rename that created the table moved all three together (`migrations/0056_review_bots_rename.sql:22`), and the ownership row was keyed by that same id (`migrations/0026_workspaces.sql:43-46`; its column was renamed at `migrations/0056_review_bots_rename.sql:35`). Because credential, configuration and owner shared one primary key, three facts the product needs could not be stated in the schema:

- **One install, several review bots.** Every configuration table hung off the bot row by `bot_id` (the eight `bot_*` tables, `migrations/0056_review_bots_rename.sql:25-43`), and so did the sandbox image (`migrations/0018_app_sandbox_images.sql:24`). The consumer resolved credentials, model overrides, custom providers and the sandbox image from the single id in `payload.botRef.appId` (`resolveCommenter`, `resolveAppConfig`, `resolveModelOverrides`, `resolveCustomProviders`, `resolveSandboxImage`, `src/pipeline/consumer.ts`), and one GitHub App was at most one row (`github_app_id INTEGER UNIQUE NOT NULL`, `migrations/0038_webhook_path_drop.sql:81`). A repository was therefore reviewed by exactly one configuration: a target was keyed by the bot (`CREATE TABLE review_targets`, `migrations/0057_review_targets.sql:40`; `resolveByRepo`, `src/dashboard/targets-store.ts`).
- **A quota per (bot, workspace).** The usage ledger recorded no bot (`recordUsageEvent`, `src/store/usage-store.ts`); its latest column was `source` (`migrations/0065_usage_events_source.sql:30`). One refusal point compared one workspace-wide sum against one plan ceiling (`quotaRefusal`, `src/worker/index.ts`), and that sum did not filter by source, so a workspace's own bot also spent its plan ceiling. The only price multipliers were two columns of the operator's profile (`migrations/0063_quota_profiles.sql:58-59`; `rpFor`, `src/store/quota-store.ts`), so a bot's owner could not price or cap its own bot.
- **Two sharing semantics.** One column answered two unrelated questions: `scope` (`migrations/0058_review_bot_scope.sql:25-27`) decided both whether another workspace might bind an installation (`appBindInstallationRoute`, `src/dashboard/index.ts`; `listPendingInstallations`, `src/dashboard/apps-store.ts`) and whether a review was platform-funded and plan-gated (`src/worker/index.ts`; `src/pipeline/consumer.ts`).

"Which workspace installed which GitHub App" had no row of its own either. It was derived from the ownership table, from `bound_workspace_id` on the physical installation (`migrations/0104_bot_installation_binding.sql:10`; `bindInstallation`, `src/dashboard/apps-store.ts`) and from "holds a live target" (`SCOPED_APP_SQL`, `src/dashboard/apps-store.ts`; `appsListWithHealth`, `src/dashboard/index.ts`).

## Decision

### Two entities and the install state

| Entity | Owns | May be shared |
| --- | --- | --- |
| **GitHub App** — `github_apps` (renamed from `review_bots` in place) | `github_app_id` (unique), `private_key_enc`, `webhook_secret_enc`, the slug and cached GitHub metadata, `status`, `review_enabled`, `last_webhook_at`, the owner workspace (`app_workspaces`), `scope` and `shared_at`, and no bot column — no `default_bot_id`; its physical installations, `github_app_installations` (renamed from `bot_installations`; webhook-maintained, one row per GitHub installation, id changes on reinstall) | its installations may be bound by several workspaces |
| **Review Bot** — `review_bots`, a table created by the split | `workspace_id` (its owner), `name`, `description`, `scope` and `shared_at`, `sandbox_image_id`, `multiplier` (a decimal greater than 0), `monthly_rp`, and the eight `bot_*` configuration tables; no App column — it belongs to no GitHub App | its capability and quota may be used by several consuming workspaces, each with its own quota |

- **A Review Bot belongs to no GitHub App; Apps and bots are many-to-many.** The mount `(workspace, App, bot, position)` is the only relation between the two. A bot has no GitHub identity of its own: it publishes as the App of the installation it is mounted on, so one bot may serve several Apps and one App may mount any number of bots. Neither side carries a column for the other — no `review_bots.github_app_id`, no `github_apps.default_bot_id`.
- **Both ids inherit the pre-split `review_bots.id`.** The credential AAD (`github_apps.private_key_enc:${id}`, `src/pipeline/consumer.ts:520`, `src/worker/index.ts:308`), the provider-key AAD (`app_provider_keys.key_enc:${id}:…`, `src/dashboard/app-config-store.ts:737-746`) and the webhook URL (`src/dashboard/manifest.ts:119`) all bind the row id, so no ciphertext and no public URL changes. Because the two ids are then equal, every column that points at the App is renamed `app_id` in the same migration; a `bot_id` column may point only at a Review Bot.
- **The install state is the parent of the chain.** `app_installations (github_app_id, workspace_id)` is a **new** table — not the physical installation rows, which stay in `github_app_installations` — and it is one workspace's install of one GitHub App. `app_install_bots (github_app_id, workspace_id, position, bot_id)` is the ordered chain under it, bound by a composite foreign key. A chain may contain any bot that is shared or owned by the installing workspace: `bot.workspace_id = installer OR bot.scope = 'shared'`, checked in the store batch that writes the row.
- **Only the installing workspace's owner or admin edits a chain** (`canManageRole`, `src/dashboard/index.ts`). The order lives per install state, not on the GitHub App row and not on the physical installation: the physical row is maintained by the webhook (`upsertInstallation`, `src/dashboard/apps-store.ts:1256`) and changes id on reinstall (`docs/specs/feature/bot-scope-and-claiming.md`, Invariants), and a shared App's owner must not impose an order on its consumers.
- **An install state is one workspace's install of one GitHub App, never the physical installation.** `bound_workspace_id` stays on the physical rows, where the webhook never writes it and its `(bot_id, bound_workspace_id)` index is not unique (`migrations/0104_bot_installation_binding.sql:10-13`), so one state row may cover several installations that workspace binds. A bind writes the state row when it is that workspace's first installation of the App, in the same batch as the proof of ownership, and writes the chain with it. Creating an App writes the owner's own state row with zero physical installations, and one chain row naming the bot the App created. Removing one of several installations leaves the state row and its chain in place; the row is removed only when the workspace holds no installation of that App and does not own it — that is the aggregate a full uninstall removes.
- **A new install state's chain is a copy of the App owner's chain on that App.** The owner's chain — the `app_install_bots` rows of `(app.id, app.owner)`, the owner being `app_workspaces.workspace_id` — is what an App brings. A first bind copies its rows in the owner's order and keeps those whose bot is shared or owned by the binding workspace; when none qualifies the chain is empty and the App's Bots tab says so. Only two batches write a chain, App creation and a workspace's first bind; neither rewrites one that exists, and creating a target writes none. A marketplace card's capability lines are the same rows, so a card promises exactly what a bind mounts. Losing the last installation of a non-owned App removes the state and its chain, and a reinstall takes a fresh copy.

### Attribution columns

| The fact a row records | Column | Tables |
| --- | --- | --- |
| Which GitHub App acted on GitHub | `app_id` → `github_apps` | `review_targets` (renamed from `bot_id`, value unchanged), `pull_requests` (keeps `ON DELETE CASCADE`, `migrations/0039_pull_requests.sql:33`), `webhook_deliveries`, `review_publications`, `review_threads`, `review_checks`, `review_findings`, `reviews` (renamed), `lifecycle_recovery_cursor`, `check_reenable_cursor`, `degraded_target_leases` |
| Which Review Bot executed | `bot_id` → `review_bots` | `reviews` (a new column, backfilled equal to `app_id`) and the eight `bot_*` configuration tables (their foreign key is re-pointed) |

A target therefore belongs to a GitHub App and a repository, never to a physical installation: one installation covers many repositories (`migrations/0067_repo_target_identity.sql:57-58` dropped `installation_id` for that reason) and the job payload already carries `installation_id` (`ReviewJobPayload`, `src/contracts/review-job.ts`). The tenant predicate is untouched: tenant reads still bind `target_id` (`migrations/0060_execution_ledger_target.sql:201`).

### Quota

- **The plan ceiling comes first and counts shared bots only.** `quota_profile_plans.monthly_rp` stays. Its used side is `SUM(rp)` over `source = 'shared'` rows of the consuming workspace for the month.
- **An own bot bypasses the plan ceiling entirely.** Its RP is still recorded per bot, for display.
- **A per-(bot, workspace) ceiling sits on top for shared bots.** `review_bots.monthly_rp` is the bot-level default; a row in `bot_quota_overrides (bot_id, workspace_id, monthly_rp)` replaces it for one workspace, and a stored NULL there means unlimited. NULL as the default means "no bot-level cap".
- **`multiplier` replaces the profile's source multipliers; it does not multiply them.** The price is `rp = max(1, ceil(base(level) × bot.multiplier))` — an integer RP, always rounded up — over base weights of 50 / 100 / 300 for quick / standard / deep, with 1 credit = 1000 RP. `quota_profiles.source_byok` and `source_shared` dropped in the release that switched `rpFor` to the multiplier (`migrations/0120_quota_profile_source_drop.sql`), and `usage_events.source` stays as the record of which category paid at charge time (`migrations/0065_usage_events_source.sql` explains why it cannot be derived later).
- **`usage_events` carries `bot_id`.** Every workspace's spend is attributed to a Review Bot, which is what "each bot's spend this month" reads. Metering writes it from `botRef.botId` (`migrations/0117_usage_events_bot_id.sql`), so no row written after the migration is NULL.
- **A workspace locks its quota version per month.** `workspace_quota_binding (workspace_id, month, profile_id)` names the profile a workspace meters under for one month. The metering path is its only writer: the same batch that appends a workspace's first usage row of a month inserts the binding with the profile in force at that instant. Every reader resolves through `resolveWorkspaceQuotaProfile` and, finding no binding, answers the profile in force now without writing. A workspace created after the split therefore uses the latest version at once, a workspace already metering this month keeps that month's version across a mid-month publish, and the first metering of the next month binds again. `migrations/0119_workspace_quota_binding.sql` pinned every month already holding usage to the profile covering that month's first day, so no month in progress was repriced, and the [entitlement spec](../../../../docs/specs/architecture/entitlement-and-deployment-modes.md) § RP metering and the monthly ceiling now states this rule in place of the first-day-of-month one.

### Relay

`selectReviewBot` stands in for the former `quotaRefusal` call at the single refusal point, the enqueue branch of the webhook route (`src/worker/index.ts`). Execution meters and never refuses (`docs/specs/architecture/entitlement-and-deployment-modes.md` § RP metering and the monthly ceiling), and never switches bot.

1. Read the chain of the target's workspace under the resolved GitHub App, in position order, live bots only. An empty chain is refused.
2. For each bot in order: an own bot is selected at once, before any quota read (no profile, no month sum, no plan).
3. A shared bot needs, in this order: the plan capability (`checkEntitlement` with `kind: "shared-bot"`, `src/dashboard/entitlement.ts`), then the plan month over shared RP, then the bot month. A bot that fails any of them is skipped and the reason is remembered; the plan month is read once per delivery.
4. The first bot that passes executes. Only when every bot failed is the delivery refused, with the remembered reason in capability > plan > bot order.

A refusal keeps the three existing surfaces: one `review_failures` row through `refuseDelivery` (`src/worker/handlers.ts`), a Check that is still attached and settles neutral (`attachCheckOnAcceptance`, `src/worker/index.ts`), and a `skipped` delivery outcome (`deliveryOutcomeFromWebhook`, `src/worker/index.ts`). A delivery records at most one refusal; skipped bots record nothing. The refusal value carries `scope` (plan or bot) and `botId`, and a bot-level refusal has its own author-facing sentence, because the author's next step differs: wait for the bot's owner, or change plan.

### Sharing

Two independent predicates and two independent switches:

| | Shared GitHub App | Shared Review Bot |
| --- | --- | --- |
| Predicate | `github_apps.scope = 'shared'` | `review_bots.scope = 'shared'` |
| What is shared | installations may be bound by other workspaces | the capability and its quota may be used by other workspaces |
| Who reads it | the bind route and the pending list (`appBindInstallationRoute`, `src/dashboard/index.ts`; `listPendingInstallations`, `src/dashboard/apps-store.ts:1359`), App visibility | the enqueue capability gate (`checkEntitlement` `kind: "shared-bot"`, `src/dashboard/entitlement.ts`) and the price source (`getBotScope`, `src/pipeline/consumer.ts:1817`) |
| Quota | none of its own | `bot_quota_overrides`, else `review_bots.monthly_rp`; spend is charged to the consuming workspace |
| Switch | "Share this App" on the GitHub App detail | "Share this Bot" on the Review Bot detail |

Only a workspace designated as the official one may share (`officialWorkspaceGuardSql`, `src/dashboard/apps-store.ts:2388`; `OFFICIAL_WORKSPACE_KEY`, `src/dashboard/runtime-config-store.ts:1422`), and the guard is evaluated inside the writing batch (`setReviewBotScope`, `src/dashboard/apps-store.ts`). That rule is kept behind one function with a single switch point, so that "any workspace may share" can later be enabled without touching either writer. Each entity has its own store function; no SQL is built from a table name.

### UI

- **The Apps page is three tabs, addressable in the URL** (`/dashboard/<workspaceRef>/apps?tab=…`; the route is `AppsPage`, `src/spa/pages/AppsPage.tsx`):
  - `installed` — **installed GitHub Apps**, the consumer's view: the GitHub Apps this workspace installed or bound, each opening an ordered list of mounted Review Bots (shared or own) with each bot's spend this month;
  - `created` — **GitHub Apps I created**, the supply view: the App detail (credentials, installations, delivery, metadata);
  - `bots` — **Bots I can use**: every shared bot plus every bot this workspace created, one list filtered by `All` / `Created by me` / `Shared`, with no App column, each opening its detail. The page opens on `installed` when the workspace has at least one installed App, else on `created`;
- **The App detail's tabs are split in two.** `delivery` and `installations` are their own tabs (`AppDeliveryTab`, `src/spa/pages/AppDeliveryTab.tsx:44`, mounted at `src/spa/pages/AppDetailPage.tsx:910`; `AppInstallSection` and `AppInstallationsSection`, `src/spa/pages/AppDetailPage.tsx:923` and `:933`). What stays on the App side is the App's own settings: GitHub metadata, enable/disable/delete (`TargetOpsZone`, `src/spa/pages/AppDetailPage.tsx:656`) and "Share this App". What moved out is the review-bot configuration, rendered by `BotSettingsView` (`src/spa/pages/BotDetailPage.tsx:224`): sandbox image, providers and keys, model chains and seats (`SandboxSection`, `src/spa/pages/BotSettingsPage.tsx:317`). The App detail also carries a `bots` tab for the chain.
- **A Review Bot detail page is new**: `/dashboard/<workspaceRef>/bots/<botId>`, in two blocks and no sub-tabs. A read-only overview serves every viewer — name, description, provider workspace, sharing state, the Apps of this workspace that mount it, multiplier, this workspace's month spend and remaining ceiling, capability summary. An editable region — model chains, sandbox, provider keys, seats, multiplier, default ceiling, per-workspace overrides — is rendered only to the owner workspace's owner or admin, and the store refuses a non-owner's write whatever was rendered. The routes join `WORKSPACE_FAMILY_SEGMENTS` (`src/spa/routes.ts:72`), which the Worker's tenant gate derives from (`src/dashboard/index.ts:630`).

### Delivery phases

The split shipped as five releases, in this order.

| Phase | Content | Shipped alone? |
| --- | --- | --- |
| P0 | The `installed` and `created` tabs over the `/api/apps` data (`appListRoute`, `src/dashboard/index.ts:5725`); the install wizard's client-side steps. No schema change. | yes |
| P1 | The split migration: `github_apps` and the new `review_bots` table, `app_workspaces`, `github_app_installations`, and the new `app_installations` and `app_install_bots` DDL; the re-pointed configuration tables; every `app_id` rename; `botRef.botId`; the consumer's resolution; the configuration routes under `/api/review-bots/:botId`; the `bots` tab and the Review Bot detail. Behaviour is unchanged: one bot per App, `multiplier` backfilled from the profile, `monthly_rp` NULL. `github_apps.sandbox_image_id` drops in a file of its own after the backfill that reads it. | **no — schema, Worker, pipeline, dashboard and SPA move in one release; migration first, then the Worker** |
| P2 | Install states and their copied chain take effect; the bind batch writes the install state; uninstall. The chain is displayed read-only in this release. | yes |
| P3a | `usage_events.bot_id` and its backfill; `multiplier` replaces the source multipliers and the two `quota_profiles.source_*` columns drop with that switch; `workspace_quota_binding` binds the quota version per workspace and month; own bots bypass the plan ceiling; each bot's spend is shown. | yes, in its own announced window: it changes billing |
| P3b | Bot-level ceilings (default and overrides), the quota editor in the bot detail's editable region, `selectReviewBot` and the relay, both sharing switches, and the editable chain order (add, remove, reorder). | with its own selection logic: the order became editable only in the release that reads it |

P1 cannot be split because the configuration tables follow the new bot row while the credentials stay on the App row: a Worker that reads one and not the other resolves half a bot. The migrations behind it are rehearsal-checked on SQLite 3.51.0 with `foreign_keys = ON` and one transaction per file — the split commits with an empty `PRAGMA foreign_key_check`, a `DROP TABLE github_apps` attempt fails on the non-cascading children's references while its `pull_requests` cascade would empty the ledger had the drop been allowed, and a pre-split row without an owner row aborts the whole migration with the schema left unsplit. That rehearsal is the SQLite CLI's, not D1's; the preview-D1 run on a production snapshot is an operator follow-up (§ Risks).

## Alternatives considered

- **Add an `apps` aggregate table and leave `review_bots` as it is.** An app listing N bots would still need N GitHub Apps installed on every repository: an installation token can only be minted by the App that owns the installation (`resolveCommenter`, `src/pipeline/consumer.ts:518-522`), and each bot row is its own webhook entry (`src/worker/index.ts:414`, `src/dashboard/manifest.ts:119`). "One installed app with several bots" would be N installs and N binds for the user, and the aggregate row would carry nothing once N bots share one GitHub App.
- **Bind the target to the physical installation.** This was tried and removed: one installation covers many repositories, which is why `migrations/0067_repo_target_identity.sql:57-58` dropped `installation_id` from `review_targets`. It would also restore the one-installation-one-target coupling that `review_targets_bot_installation` enforced (`migrations/0057_review_targets.sql:72-74`), while the executing installation is already on the job payload (`ReviewJobPayload`, `src/contracts/review-job.ts`).
- **Relay by switching to another GitHub App** (each bot keeps its own credentials). The comment author and the Check-run App would change at every relay, and `@mention` resolution follows the App's slug (`payloadMentionsALogin`, `src/worker/webhooks.ts:133`). The user would install and bind N GitHub Apps; there would be N webhook entries, and the Check would have to be created with the selected bot's credentials while `attachCheckOnAcceptance` uses the entry row (`src/worker/index.ts:295`). The platform would rotate N keys, the cost [shared bot scope and claiming](../feature/2026-11-15-shared-bot-scope-and-claiming.md) already rejected when it refused to copy the App per consumer.
- **One independent RP pool per shared bot, with no plan total.** It would retire the versioned ceilings the operator publishes per plan (`resolveWorkspaceMonthlyQuota`, `src/store/quota-store.ts:155`; `src/admin/quota-versions.ts`), and a workspace's total spend would become the sum of every mounted bot's pool, so mounting one more bot raises the total with no plan change. Free and pro would no longer differ in their monthly review ceiling (`migrations/0063_quota_profiles.sql:83-87`). The plan ceiling is kept, with the bot ceiling on top and NULL by default.
- **Multiply the profile's source multiplier by a per-bot multiplier.** A shared bot would cost `base × 10 × up to 10`, because `source_shared` is 10 (`migrations/0063_quota_profiles.sql:78`), and two places would state the same fact, which is the defect `migrations/0065_usage_events_source.sql` records for a single `rp` value. `multiplier` replaces the source columns instead: an own bot is backfilled with 1 and a shared bot with the profile's `source_shared`, so no stored price changes.
- **Keep each Review Bot on a host GitHub App, with `github_apps.default_bot_id` naming the bot an install starts with.** A host App makes "any App may mount the same bot" unstatable, and one default column cannot describe the several bots a marketplace card lists; it would be a second App ↔ bot relation beside the mount, read by nothing else. The mount is the only relation.
- **Start a new install on an empty chain, on a bot chosen at bind time, or on the first target creation.** An empty chain refuses every delivery until someone edits it; a choice at bind time is a step the user does not have today; a target row is not an install state and may be created long after the bind. The owner's chain is copied instead, so behaviour is unchanged for every install that exists.
- **Write the quota-version binding on first read.** A reader that writes locks a version for a workspace that has not metered, which defeats "a new workspace uses the latest version at once", and it makes every reader a second writer — the mid-month version jump the binding exists to prevent.
- **One migration file per `DROP COLUMN` statement, or all three in the split's own file.** No drop file becomes re-runnable by standing alone, while a backfill must stay re-runnable; and the two `quota_profiles.source_*` columns cannot drop before the release that stops `rpFor` reading them.

## Consequences

- **The split migration is idempotent and foreign-key sound.** Replaying the backfill inside the split transaction leaves exactly one `github_apps` row and one `review_bots` row per pre-split row, carrying the old id; `PRAGMA foreign_key_check` is empty over populated data, the eight `bot_*` tables reference `review_bots`, every publishing column references `github_apps` as `app_id`, `review_bots` has no `github_app_id` and `github_apps` has no `default_bot_id`, and `pull_requests.app_id` keeps `ON DELETE CASCADE` (the one child a parent rebuild would empty rather than refuse). `tests/store/app-bot-split-migration.test.ts` — "the backfill file executed twice inside the split transaction is a fixed point — one row pair per pre-split row", "PRAGMA foreign_key_check is empty over populated data", "a pre-split row without an owner row aborts the whole file and leaves the schema unsplit". The replayable backfill is `scripts/app-bot-backfill.sql`, not a second application of the apply-once migration file.
- **One entry per GitHub App, unchanged.** The webhook route stays `POST /webhook/:workspaceId/:appId` (`src/worker/index.ts`) with one secret per App; a Review Bot holds no `webhook_secret_enc`, and two bots under one App publish reviews and Check runs under the same `github_app_id`. `tests/worker/webhook-routing.test.ts` covers the route.
- **No Review Bot references a GitHub App.** Neither table carries a column for the other, and one bot sits in the chains of two different Apps: `app_install_bots` is keyed `(github_app_id, workspace_id, position)` with `bot_id` a plain foreign key (`migrations/0115_app_bot_split.sql`), and every chain read is scoped by `(github_app_id, workspace_id)` (`CHAIN_SQL`, `src/worker/select-review-bot.ts`). `tests/store/app-bot-split-migration.test.ts` — "neither entity carries a column for the other (D34)".
- **An own bot never refuses for quota.** With the chain's first bot owned by the consuming workspace and that workspace past its plan ceiling, the delivery is enqueued and no `review_failures` row is written on the `quota` stage; no quota read is issued before the selection. `tests/worker/select-review-bot.test.ts` counts the statements the relay issues against the quota tables.
- **Chain order decides the executing bot.** With the chain `[A shared with quota left, B own]`, A executes; with A exhausted, B executes, and the enqueued job's `botRef.botId` names that bot while `usage_events.bot_id` records it. `selectReviewBot` (`src/worker/select-review-bot.ts`) is the walk, and `tests/worker/select-review-bot.test.ts` covers the order and the four-step refusal precedence.
- **A new install state starts on a copy of the App owner's chain.** Creating an App leaves the owner's state with one chain row naming the bot the App created; a workspace's first bind copies the owner's chain rows whose bots are shared or owned by that workspace, in the owner's order, and copies no other; a later bind for a workspace that already holds the state changes no chain row; a marketplace card lists the same bots for the same App. `tests/dashboard/install-state-lifecycle.test.ts` covers the copy and its lifecycle.
- **A plan refusal and a bot refusal can be told apart.** `RelayRefusal` carries `quota-plan` and `quota-bot` as distinct values (`src/worker/select-review-bot.ts`), each with its own author-facing sentence in `deliveryRefusalReason` (`src/worker/handlers.ts`), and both come from the single enqueue refusal point; one delivery writes at most one failure row.
- **`usage_events.bot_id` attribution is reported to the operator.** The `usage-bot-attribution` data-upgrade item reports how many pre-migration rows with `rp > 0` carry a `bot_id` and how many are left NULL — `verify` returns `attributable_rows` and `permanently_unattributable_rows` (`src/admin/data-upgrades/usage-bot-attribution.ts`) — and every row written after the migration carries a `bot_id`. `tests/admin/usage-bot-attribution.test.ts` pins that a zero queue holding unattributable rows is reported rather than answered as zero, and that its buckets are disjoint and sum to the permanent total.
- **Only the metering path writes `workspace_quota_binding`.** The first usage row of a month and its binding land in one batch whose first statement is `INSERT OR IGNORE INTO workspace_quota_binding` conditioned on no usage row existing (`chargeUsage`, `src/store/usage-store.ts`); a second metering that month writes no binding even across a mid-month publish, the first metering of the next month binds again, and no reader writes one — a workspace that only opens its quota page holds no binding row.
- **The two sharing switches do not affect each other.** Sharing a GitHub App changes no bot's `scope` and no review's price source; sharing a bot without sharing its App leaves the bind route refusing exactly as it did before the split (`appBindInstallationRoute`, `src/dashboard/index.ts`). `tests/dashboard/share-switches.test.ts` covers both columns and both guards.
- **Supersession.** This record replaces [the one-bot-entity decision](2026-11-15-review-bot-and-target-entities.md) — what that record states as one entity is here a GitHub App (identity, installations, publishing) and a Review Bot (configuration, quota), meeting only in the per-install chain — and, in part, [the shared-bot scope record](../feature/2026-11-15-shared-bot-scope-and-claiming.md): its `scope` answered both "may another workspace bind this installation" and "is this review platform-funded", and the two questions are here two switches. That record's designation, its bind refusal and its retired claim stand.

## Risks

**Key risks carried from the assessment.**

- **Data backfill (R4).** The App row can only be renamed, never rebuilt. A rebuild's `DROP TABLE github_apps` empties `pull_requests` through its `ON DELETE CASCADE` (`migrations/0039_pull_requests.sql:33`) — that child cannot refuse the drop — while the non-cascading children leave foreign-key violations, so the rebuild cannot commit; `migrations/0057_review_targets.sql:29-33` records the same mechanism. The split ships with CHECK-constrained guards inside the migration, and migration before Worker. The rehearsal behind it runs on the SQLite CLI; a production-snapshot rehearsal in a preview D1 is an operator follow-up, not a condition of the decision.
- **Pricing switch (R12).** `multiplier` is backfilled from the profile in force, so no stored price changes, but the operator loses a per-version multiplier. `tests/worker/admin-quota-versions.test.ts` follows the switch.
- **Own bots are uncapped (R8).** This supersedes rule D7 of the [entitlement spec](../../../../docs/specs/architecture/entitlement-and-deployment-modes.md), which said "BYOK is metered, never exempt"; the spec now states the own-bot bypass. The remaining cost gates are `workspaces.max_concurrent_reviews` and `apps_per_workspace`; an own bot's spend is recorded and shown, not alerted on.
- **In-flight jobs without `botId` (R7).** Messages queued before the split, and payloads persisted by `comment_trigger_claims` (`src/worker/handlers.ts:323`) and by maintenance replay (`src/admin/maintenance-replay.ts`), predate the field. `migrations/0115_app_bot_split.sql` rewrites the queued rows in place and the replay tool names the bot; the queue drains inside the maintenance window.
- **Three kinds of writer (R5).** The App owner, the bot owner and the installing workspace each write different things. A bot's write permission is judged on `review_bots.workspace_id` through `setReviewBotScope`'s own re-check (`src/dashboard/apps-store.ts`), not on the App row.
- **Re-runs may land on another bot (R1).** The publishing identity is stable; only the executing configuration can differ between two runs of one head.
- **Blast radius (R4, R13).** Non-test sources touching the renamed identifiers, counted at commit `1981816d` with `grep -rlE <identifier> src` over `*.ts` and `*.tsx`: `review_bots` in 19 files, `bot_workspaces` in 3, `bot_installations` in 11, `bot_id` in 23. Twelve index names still contain `bot` after the rename; renaming them is optional.
- **Documentation drift (R14).** Every record and spec this decision changes is named in [ADR impact at promotion](#adr-impact-at-promotion), and that table now states each row's outcome. The entitlement spec's shared-bot gate on target creation has no counterpart in code (`SHARED_BOT_REFUSAL` has no caller in `src/`, `src/dashboard/entitlement.ts`), so that correction stands on its own, independent of the split.

**Known gaps.**

- **Existing usage is only partly attributable.** The backfill joins `usage_events.review_id` to `reviews.id`, which holds when the job payload carried a head (`idemKey` in both places, `src/pipeline/review-attempt-execution.ts:3235` and `:4675`). A comment-triggered job carries `head_sha: null` (`src/worker/webhooks.ts:721`), so its usage id says `no-sha` while its review id says the resolved sha, and those rows stay NULL — permanently, which is why the attribution item reports them separately instead of failing on them.
- **The 286 test files are not inventoried** (`find tests -name "*.test.ts" -o -name "*.test.tsx"` at commit `1981816d`). The P1 figure is a per-identifier count, not a per-test plan.
- **The D7 sentence is corrected in the spec.** The entitlement spec states the own-bot bypass (see R8 above), and this record is the one that replaces D7.
- **Sharing from any workspace is a future item.** Only the official workspace may share (`officialWorkspaceGuardSql`, `src/dashboard/apps-store.ts:2388`); the guard is switchable, not switched.
