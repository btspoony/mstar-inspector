# Feature: App detail visibility

## Scope

Dashboard App detail routing, the App detail's two faces (installed mount / creator), the mount chain's read/write boundary, the Review Bot directory and archive state, member identity-only reads and manager-only operational data.

## Current state

### App detail contract

| ID | Contract |
|----|----------|
| D2 | Insights and pull requests are read at exactly two scopes: one repository target and the whole workspace behind the 所有仓库 entry. No application-scoped and no deployment-global face exists. |
| D3 | `/dashboard/apps/:appId` (the numeric `github_app_id`) is the **应用详情 (App detail)** page. One route, **two faces** selected by the served `viewer_relation` (`installed` / `created` / `both`) and, for `both` only, the `?from=` origin the list recorded: the **installed face** (a mount: read-only App facts, install/bind state, the workspace's editable mount chain, no tab bar) and the **creator face** (three tabs: **应用设置**, **投递状态**, **已安装**). Review policy belongs to the repository detail, `/dashboard/{workspaceRef}/repos/<targetId>` (target UUID). The App detail links back only to the Apps list: the repository surface is not reachable backwards from here. |
| D4 | A member without the workspace owner/admin role sees **GitHub App identity info only** on the creator face. The identity set: `github_app_id`, `status`, `review_enabled`, `created_by`, `created_at` — the App identity fields, plus creation time — **and** the App's cached public GitHub profile (`github_name`, `github_slug`, `github_description`, `github_html_url`, `github_avatar_url`, `github_metadata_synced_at`), plus local App `id` and top-level server-resolved `workspace_id` (the pair composing the manager-visible webhook URL). Operational fields — `delivery_summary`, `last_webhook_at`, `sandbox_image_id`, the settings payload — remain behind the `canManageApp` branch; insight and pull-request reads 403; every mutation 403. Non-managers receive no operational payload. `review_trigger_mode` is not an operational field of the application: it is a target-owned fact the payload echoes as read-only context only when the workspace holds exactly one target under the app. **Install state is not one of those operational fields**: the App detail serves this workspace's own `installations` and `chain` to every member — they are what the workspace mounts, and the installed face exists for exactly that reader. |
| D5 | Insight and pull-request reads are **workspace owner-or-admin** at both scopes: the target routes (`…/api/targets/:targetId/insights/summary`, `…/pull-requests`) and the workspace routes (`…/api/insights/summary`, `…/api/pull-requests`), both gated by `canManageApp`, which is `canManageRole(scope.role)`. Creating an App grants nothing: the creator of an App they are a plain member of gets the same 403 as any other member. |
| D6 | The Apps list stays visible to all members with its current columns/payload; every row links into the detail page. The list renders exactly one manage affordance today — the manager-only **Bind** action on a pending installation row, served with the server's own `can_bind` and withheld for members — and no other; any affordance added later must be `can_manage`-gated. |

### Information architecture

- `/dashboard/apps/:appId` → App detail page (D3), with the workspace-scoped twin `/dashboard/{workspaceRef}/apps/{github_app_id}` served by the same page id and consuming `GET /api/apps/:appId`. One route, two faces:
  - the **installed face** — `viewer_relation` is `installed`, or `both` opened with `?from=installed`. Read-only App identity (name, creator, GitHub App ID), a metric band of 挂载的机器人 / 安装 / 本月已用 (Credits), the install/bind block and this workspace's mount chain. No tab bar, no credentials, no share switch, no delete/enable, no metadata refresh, no delivery. The chain is the one write surface here: the installing workspace's owner/admin gets ↑↓✕ on the rows and 添加机器人 in the section header; a member sees the same rows with the controls absent.
  - the **creator face** — `viewer_relation` is `created`, or `both` without `?from=` (or with `?from=created`). Tab set 应用设置 | 投递状态 | 已安装, derived from `?tab=`; a request without the parameter lands on 应用设置. 应用设置 renders ONE GitHub App section (identity plus credential state), the operations block and the share switch (the official workspace only, with the non-official read-only line). No bots tab, no chain, no repository block.
- **The face follows the served relation, never the URL alone.** `from` selects between faces only when the relation is `both`; an installed-only App is a mount whatever the URL says, and a created-only App opens as its owner's creation. Authorization stays server-side: `canManageApp` gates every creator route and field with ONE explicit exception — the paged delivery log `GET …/api/apps/:appId/deliveries` is member-readable (it gates on `requireMember` and narrows non-owner reads to the caller's workspace), as the authorization matrix above states; the chain write is checked by the store's installer gate.
- The legacy list spelling `/dashboard/{workspaceRef}/apps?tab=bots` answers one 302 to the same workspace's `/bots`, and the Apps page replaces it client-side too — including a history entry whose resolved tab would not otherwise change. On the App DETAIL, `?tab=bots` is not an address: it resolves to 应用设置.
- The retired spellings `…/apps/:appId/settings` and `…/apps/:appId/bot` each answer one 302 to the canonical `…/apps/:appId?tab=settings`. The retired app-target policy POST family and its redirect helpers are deleted with the routes. A completed installation bind lands on the App's installed face (`?from=installed`) — where its new chain is shown.
- A non-manager keeps the D4 identity-only payload on the creator face; the install-state slice (`installations`, `chain`) is served to every member because it is what the workspace mounts.
- `/dashboard/{workspaceRef}/bots` is a first-class page: two sections (我创建的机器人 / 共享给我的机器人), each row the bot's name with its description, the id as muted meta, the archived state as a muted 已归档 pill. 创建机器人 lives in the 我创建的机器人 section header. `/dashboard/{workspaceRef}/bots/:botId` is one route with two readings: the owning workspace's owner/admin gets 概览 / 配置; every other workspace gets the same header and metric band plus 使用情况 / 能力摘要 / 挂载于 with **no tab bar**. Archive is a restorable retirement state: the row stays listed, the relay skips it, and its configuration is read-only except 恢复.
- `/dashboard/insights` is removed from `SPA_PAGES`, the sidebar, and i18n nav keys. Deep links to it fall through the normal unknown-route behavior (no longer shell-served: an HTML GET falls past the SPA dispatch to the guarded dashboard app's 404, exactly like any other unknown `/dashboard` path).
- Sidebar: five entries in the order 仓库 / 应用 / 机器人 / 成员 / 设置, from one source (`NAV_ITEMS`); the repository entry uses `FolderGit2` and the bots entry `Bot`.
- Apps list: every row navigates to the detail page and records its origin in the link (`?from=installed` / `?from=created`); the row action's copy moves from settings semantics to detail semantics in both locales. The shared-App chooser (the header's create dialog and the installed empty state's browse action) applies ONE eligibility rule — an App this workspace already installed is never offered again. Beyond the manager-only Bind action on pending installation rows (D6), the list renders no manage affordances and must not grow any that are not `can_manage`-gated (D6 invariant); columns and the list payload are otherwise unchanged.

#### Units

RP is the internal accounting unit; every user-facing amount, ceiling and spend figure renders in **Credits** with two decimals (`1,000 RP = 1 Credit`, and the documented fallback rate when the operator profile is unreadable and the payload omits `rp_per_credit`). A figure labelled 本月 is always 本月已用 and states its ceiling (`已用 / 上限`), its known-unlimited state (不限) or its own-bot state (不限（自有机器人）) — never a bare number the reader must guess at. An own bot is never priced by its multiplier, and an unshared bot has no consumer, so both read ×1 wherever an effective multiplier is stated.

#### App identity key

- **Every path above carries the numeric GitHub App id**, including the workspace-scoped form `/dashboard/{workspaceRef}/apps/{github_app_id}`, all `/api/apps/:appId/…` routes, and every server-generated redirect. A non-numeric segment is a 404.
- The numeric GitHub App id addresses detail routes; neither the former local slug nor cached `github_slug` addresses a detail URL. Old local-slug bookmarks have no redirect. Migration `0036_app_identity.sql` renamed the local slug to `webhook_path`; `0038_webhook_path_drop.sql` removed that duplicated key entirely. Webhook delivery uses `/webhook/{workspaces.id}/{github_apps.id}` with no single-segment compatibility route.
- The Apps list payload loses `slug` and gains `github_name` / `github_slug` / `github_avatar_url`; the display name falls back `github_name ?? github_slug ?? String(github_app_id)`, and the avatar is the App's own logo (the bot account's avatar), not the owner's.

### Data faces

- `insights-store` binds a target-id set (`ledgerScopeSql` promoted to `targetIds`); the workspace scope resolves the workspace's live targets in a subquery, so the bind count stays constant. No application-scoped filter exists.
- `GET …/api/targets/:targetId/insights/summary` and `GET …/api/insights/summary` — same `window` / `repo` / `include=repos` semantics and payload keys, manager gate, and malformed params answering 400.
- `GET /api/apps/:appId` (SPA data face; the bot-settings sibling `GET /api/review-bots/:botId/settings` parses through the same SPA shape but carries no App identity and no install state) — every branch carries `viewer_relation` and, when the operator profile is readable, `rp_per_credit` (absent otherwise; the SPA then charges the documented 1,000 RP fallback). The `can_manage: false` base payload contains the D4 identity set + `can_manage: false` **plus this workspace's own install state** (`installations`, `chain`) — and the absence of `delivery_summary`, `last_webhook_at`, `sandbox_image_id`, `pending_installations` and the bot-owned sections. An unblocked manager receives the operational shape, plus `pending_installations` for a shared App (empty for an owned one, which can never bind) — but only the App's OWNING manager receives it in full: an installer manager (this workspace does not own the App) is served the installer-scoped projection, which keeps the install state, the chain, the roster and `can_configure_bot` and withholds `last_webhook_at` / `github_metadata_synced_at` / `delivery_summary` (`src/dashboard/index.ts:2625,2754,2803-2808` — the `creator`/`owned` split). A BLOCKED manager receives neither the operational sections nor `pending_installations` — it has no bind action to offer.
- `GET …/api/apps/:appId/deliveries` is a separate paged read, not a fixed list on the settings payload: it takes `repo` / `since` / `type` / `offset` and answers the matching `total` plus the App's unnarrowed `repos` / `types` option sets, so the tab filters and pages on the server. A malformed parameter is a 400; a well-formed value matching nothing is an empty page with `total: 0`. The response is exactly `deliveries` (each row: `event_name`, `outcome`, `status_code`, `repository_full_name`, `reason`, `created_at`), `total`, `repos` and `types` — it carries **no review facts**, no allowlist and no `owner_overlap` field.
- The review facts belong to the App DETAIL response, per branch. A manager of the App's OWNING workspace always gets top-level `targets_many`; with a target it also gets `target_id` + `check_gate` at the top level and `review_enabled` / `review_trigger_mode` / `review_level` / `default_review_level` inside `app`, and with none all six of those keys are absent (only `targets_many: false` remains). An INSTALLER manager — a caller that manages its own workspace but does not own the App — is served the installer-scoped projection instead: `targets_many` still states the fact, while `target_id`, `check_gate` and the four `app.review_*` fields are absent, because that policy slice belongs to the creator (`src/dashboard/index.ts:2723-2739` `targetOwned`). A BLOCKED manager always gets `targets_many` and `target_id` — `null` when the workspace holds no single live target — and the same four `app` fields plus `check_gate` only when that target exists. A non-manager gets no `targets_many` and no `check_gate`: `target_id` appears only when the workspace holds exactly one live target, and `app.review_enabled` only with it.
- `PATCH …/api/apps/:appId/chain` is the one chain write: `{ botIds }` in order, refused when this workspace is not the App's installer (`not_installer` → 404), when any NEW id is neither shared nor owned here and not already mounted (`bot_unavailable` → 400), or when the rewrite would push the chain product outside the NEW-mount write bound — at most `CHAIN_MULTIPLIER_MAX`, and strictly positive — (`chain_too_large` → 400; `src/dashboard/apps-store.ts:1839-1878`). The store re-inserts positions contiguously in one guarded batch, so a refused rewrite leaves the old chain byte-identical. The product is computed inside that batch from the multipliers stored at write time; a rewrite that mounts no id the chain does not already hold is admitted even past the bound, so an out-of-domain chain can still be repaired by removing from it.
- Chain rows project only what the reader may see: `effective_monthly_rp` is the ceiling the relay enforces for THIS workspace (its override, else the bot's default), and the owner's raw `monthly_rp` is never served. An unshared mount keeps its availability, name and recorded spend; the owner's `default_chain` and `runtime` drop to `null`.
- `GET /api/review-bots` (the bot directory's list) serves each row's `effective_ceiling` — the same per-workspace override-else-default resolution, correlated on the caller — plus `archived`; the payload's `plan_monthly_rp` is the workspace-wide plan fact, never a row's ceiling. `quota_error: true` marks an unresolved ceiling; it is an error state, never "no ceiling".
- `GET …/api/review-bots/:botId/bot` serves the bot's own face: identity, the read-only overview (使用情况 facts, default chain, mounts) to every viewer, and the writable sections plus `quota_overrides` / `official_workspace` / `monthly_rp` only to the bot's owning workspace's owner/admin. An archived bot answers `archived: true` to every viewer and refuses every configuration write.
- Every new amount field is parsed against its wire domain (`isRpCeiling` / `isBotMultiplier` / `isServedChainProduct` in `src/contracts/rp-limits.ts`): a malformed ceiling, multiplier or rate fails the parse rather than rendering a wrong figure, and a missing REQUIRED `overview.effective_ceiling` fails it too — only an explicit `null` means "no bot-level ceiling".
- A list row's `month.multiplier` is the mounted CHAIN's product, so it is guarded by `isServedChainProduct` — any positive finite product, with NO read upper bound (`src/contracts/rp-limits.ts:93-95`). The read side never re-applies `CHAIN_MULTIPLIER_MAX` or the single stored value's `BOT_MULTIPLIER_MAX`: a legal price edit or a sub-1 removal lifts an admitted product past them, and refusing that would fail the whole list. Two legal 100× bots therefore serve `10000`, and a chain repriced to `10,000,000` also parses. The route accumulates the product without an intermediate overflow and independently of mount order (a mantissa and a power of two, with the scale applied once and halved across two multiplies, `src/dashboard/index.ts:2148-2173`), so a pure reorder of the same factors serves the same value bit-for-bit, and a chain whose every left-fold step is `Infinity` but whose product fits (`1000×` 103 times ahead of the sub-1 factors, or `1000×` 106 times with five `0.01`) still serves a finite product. It is refused only when the mathematical product is outside the double range — the scale over- or underflows — and then it answers `500` naming the unrepresentable factor rather than serving `Infinity`.
- The multiplier has the same split. A WRITE must be inside `isBotMultiplier` — at least `BOT_MULTIPLIER_MIN` (0.01), so a realistic chain's product of legal factors stays strictly positive in floating point, and at most `BOT_MULTIPLIER_MAX`. The floor does not make EVERY legal chain representable: ~162 mounted `0.01` factors already underflow a double, and such a chain is refused like any other product outside the double range. A STORED multiplier is read under `isStoredBotMultiplier`, which drops the floor: a row priced before it existed still renders, and `rpFor` charges it as `max(1, ceil(base × multiplier))`. The served product is refused only when no double holds it — `0`, a negative, `Infinity` or `NaN` — and the chain write refuses a NEW mount that would produce one before it is served.
- The credit rate has one WRITE domain and a wider READ domain. A new version's `rp_per_credit` must be a positive whole number no larger than `RP_PER_CREDIT_MAX` (`isRpPerCredit`), or every real spend would render as `0.00`. A STORED rate only has to be a positive whole number (`isStoredRpPerCredit`): the column's own CHECK is `rp_per_credit > 0`, and a row authored before the bound existed must still open the page. Consequence: such a legacy rate renders amounts very close to `0.00` on every Credits face until the operator authors a new version — the page does not fail, and no migration rewrites it.

### Non-goals

- No new roles beyond `admin` / `member`; no per-App ACL or sharing model.
- No change to review engine, publication or gate evaluation. Webhook routing now resolves the target by repository identity, described on the repository target model page.
- No data migration is needed for the new scopes: the ledger already carries `target_id` (`0060_execution_ledger_target.sql`) and workspace scope resolves through `review_targets.workspace_id`. App identity routing follows migrations `0036_app_identity.sql` and `0038_webhook_path_drop.sql`.
- No redesign of the Apps list beyond affordance gating (D6).
- No Apps-list field-level narrowing this contract: status/health/creator columns stay member-visible as today (locked by D6). Whether non-managers should see the list's health column for Apps they do not manage is an **open product question**, deliberately not decided here (owner PM; trigger = explicit user request after live use).
- No deployment-global variant: the workspace scope replaces the former global face.

## Invariants

- One App detail route, two faces, chosen by the SERVED `viewer_relation`; `?from=` only breaks the tie when the relation is `both`. The installed face carries the App facts read-only and ONE chain control surface (row ↑↓✕ + 添加机器人 in the section header), absent for a member; the creator face carries exactly three tabs and no chain. Review policy lives on the repository detail keyed by target UUID. Both retired settings/bot spellings answer one 302 to `?tab=settings`, and the completed install bind lands on the installed face.
- The install-state slice (`installations`, `chain`) is what THIS workspace mounts and is served to every member; `pending_installations` is served to every member only on the LIST (with `can_bind`), never on the member's detail face. The App's credentials, delivery payload, runtime config and bot-owned sections stay behind `canManageApp`, and the chain WRITE stays behind the store's installer gate (the caller's workspace must be the install's own owner/admin).
- `/dashboard/{workspaceRef}/bots` exists in the sidebar with two sections; `/dashboard/{workspaceRef}/bots/:botId` gives the owning workspace's owner/admin 概览 / 配置 and every other workspace a tab-bar-less read-only face. Archive is restorable: the row stays listed, the relay skips it, and its configuration is read-only except 恢复.
- RP never renders; every amount, ceiling and spend figure is Credits with two decimals, and every 本月 figure states 本月已用 with its ceiling or its unlimited/own-bot state. An own bot and an unshared bot read ×1 wherever an effective multiplier is stated.
- The scope predicate is a bound target-id set composed alongside `windowEraWhere`; no application predicate exists.
- SPA and API ship in one Worker bundle; every new amount field parses against the shared RP domain, and a missing REQUIRED ceiling is a parse failure — never "unlimited".
- Membership bootstrap, invitations, removal, role flows and per-request membership guards retain their contracts.

Keep every authorization matrix row pinned, including field absence rather than display-only hiding. Update routing, faces, tabs, row links, redirects, en/zh-CN keys and parsers with payload changes.
