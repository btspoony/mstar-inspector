# Feature: operator data upgrade

## Scope

The operator-owned machinery for data migrations too large to run as a schema change: the maintenance window, the upgrade registry and its state machine, repository identity backfill, attribution of ledger rows that never had a target, and alignment of ledger rows whose target names another repository. It also fixes how this machinery couples to the ordinary schema migrations that ship beside it. The alignment item additionally claims a target's numeric repository id from a live installation, through the same GitHub client the settings page uses.

Ordinary schema migrations stay forward-only SQL files and are never upgrade items. The product-facing wording shown during the window is part of the repository surface page; this page fixes the technical contract. Out of scope: per-workspace maintenance, an ETA promise, and any user-visible surface of the upgrade state beyond the operator console.

## Current state

### Maintenance window

| ID | Contract |
|----|----------|
| M1 | The window is three rows in the platform parameter store: `platform.maintenance.enabled` (`'1'` \| `'0'`), `platform.maintenance.reason` (operator-set text) and `platform.maintenance.since` (ISO-8601 UTC). An absent `enabled` row is the documented default — the platform is open — and that default lives only in the read helper, never in a deploy-time constant. A read fault is NOT that default: the helper answers a third state, `unreadable: true` (with `enabled: false`), logs one `maintenance_read_failed` line, and every gate treats it as CLOSED, so a settings outage can never unlock traffic while the window is the only fence around the destructive backfill. |
| M2 | One helper reads the window in a single statement over the three keys, with absent rows reading as open and no cross-request cache. Each consumer reads once per unit of work: the dashboard middleware once per request (cached on the request context), the webhook once per delivery, the queue consumer once per invocation, each cron entry once per invocation. |
| M3 | A dashboard request while the window is open answers the maintenance page instead of its content: 维护中, the operator's reason, the start time, and the closing sentence that the upgrade resumes service when it finishes. No ETA is promised. |
| M4 | A workspace API request answers `503 { "maintenance": true, "reason": …, "since": … }`. A webhook delivery answers `503` so GitHub retries it: the user-facing claim is that a delivery made during the window is retried after recovery, not dropped. |
| M5 | The queue face defers instead of running: every message of the batch is retried 300 seconds out. When the runtime offers no delayed redelivery, or a message has exhausted the queue's attempt budget, the delivery is recorded as a `review_failures` row (`stage = maintenance_deferred`, the payload's target/installation/repository/PR identity, error prefixed `maintenance_window:`) and acked, so the sweep counts it and alerts; the invocation writes one `maintenance_defer` line naming the queue and the batch size. A deferral spends one delivery attempt, so the window must stay shorter than the queue's retry budget. |
| M6 | A cron invocation does not run its work while the window is open: it records a `maintenance_skip` line naming the cron expression and returns, so the next scheduled invocation runs. |
| M7 | Not gated: `/healthz` (liveness is not maintenance), the operator console and its API, and the two pre-session dashboard paths `/dashboard/login` and `/dashboard/oauth/callback`. `/dashboard/locale` and `/dashboard/logout` stay reachable for the same reason — a session-less language toggle and burning one's own cookie are not tenant reads. |
| M8 | The operator writes the window through the existing `PATCH /_internal_admin/api/runtime` route, which accepts exactly one of `concurrency`, `checkBudgets`, `commentClaim`, `reviewLevel`, `recheckAssignment`, `maintenance` per request; the `maintenance` body is `{ enabled, reason? }`. The store writes the three keys with one platform audit event in the same batch, and enabling stamps `since` with the request's instant. |
| M9 | The upgrade runner opens and closes the window through the same helper, so there is exactly one writer path and no second API. A window the runner opened and a window the operator opened are distinguishable in state (`maintenance_owned`), never by inspecting the reason text. |

### Upgrade registry and state machine

| ID | Contract |
|----|----------|
| U1 | An upgrade item is `{ id, title, impact, requiresDowntime, order, preflight(db) → counts, runBatch(db, cursor, actor) → ONE transaction, verify(db, { runStartedAt }) → read-only checks, advisoryChecks? }`. The runner passes the operator's login as `actor`. `preflight` and `verify` write nothing. A count named in `advisoryChecks` is reported and never fails the item. The registry lists three items in order: `repo-backfill` (10), `orphan-ledger-attribution` (20), then `ledger-target-alignment` (21). A `runBatch` call also carries an optional `UpgradeRunContext`: the GitHub face (`repoLookup`) an item that claims a numeric repository id asks through, so a batch reads the network through a seam the runner owns rather than importing the GitHub client itself. An unregistered id is the operator API's 404. |
| U2 | State lives in `operator_data_upgrades`: `id` (primary key), `status` (`pending` \| `running` \| `verifying` \| `completed` \| `failed`, enforced by CHECK), `cursor_json`, `processed`, `maintenance_owned` (0/1), `started_at` (the per-phase claim), `run_started_at` (when the current run began), `finished_at`, `last_error`, `log_json`. An absent row is `pending`: the item was never started. |
| U3 | The console reads `GET /_internal_admin/api/data-upgrades` — every registered item with its state and preflight counts, one state read for the whole list — and writes `POST /_internal_admin/api/data-upgrades/:id/preflight \| step \| verify \| reset`. These routes are operator-only. |
| U4 | `step` runs from `pending` or `running` and leaves the item `running`: the item's batch is one transaction (its statements commit or roll back together), then the progress write records the new cursor, the processed count and an appended log entry. A worker that dies between the two leaves the previous cursor, and the next step re-plans from it — safe because every item's worklist excludes finished work. An empty batch answers `done: true` and the item still stays `running` until an explicit verify. |
| U5 | A `requiresDowntime` item refuses `step` while the window is closed — except its first step from `pending`, which opens the window and records ownership. `maintenance_owned = 1` means the runner owns the window and may close it; `0` means the window belongs to the operator and the runner leaves it open. A refused step or verify answers `409` with the reason and the unchanged state, so the console can name why nothing ran. |
| U6 | `verify` runs from `running`, `verifying` or `failed` (a verify interrupted mid-flight is retryable), touches no migrated data — only the item's own state row — and settles the item: any non-zero blocking check makes it `failed` with `last_error` naming the failing checks, all blocking zero makes it `completed` with `finished_at`. It reads `run_started_at` and passes it to `verify` as `{ runStartedAt }`, so the item can date what this run touched. An advisory check is reported in `checks` and the ledger row and never fails the item. Only a successful verify closes a window the runner owns, and it flips `maintenance_owned` back to 0 so a later pass cannot re-close an operator window. |
| U7 | `reset` moves any state to `pending`, clears the cursor, the processed count and the timestamps, the last error and the ownership flag, and never undoes migrated rows — replay is a no-op pass because the worklist excludes finished work. It KEEPS `run_started_at`: that stamp is the item's lifetime boundary, not a per-attempt value, so rows retired by an earlier attempt of the same item still block verify while only deletions predating the item count as history. It closes a window the runner owned and leaves an operator-enabled window open. The batch log survives, as the only record of what earlier batches discarded. |
| U8 | Every mutating phase is single-flight per item. `step`, `verify` and `reset` each claim the row with one conditional upsert (`status` set plus a five-minute `started_at` lease); a caller that loses the claim is refused with `409 upgrade_running` and the unchanged state, never a second batch. The claim is cleared in the same statement set that writes the phase outcome, and a thrown phase releases it before rethrowing. Two operators, or two tabs, therefore cannot plan the same worklist and insert one target per repository each. |
| U9 | Every card renders the item's `impact` sentence from the registry. When preflight reports at least one count and all counts are zero, the card states “Nothing to migrate — this upgrade has no work left” and disables Start or Continue; zero is not a completed run. |
| U10 | Pending and completed cards offer no reset. A running or verifying card offers “Return to pending” (`回到待开始`); a failed card instead offers “Restart upgrade” (`重新开始升级`) with “Rows already migrated are not rolled back” (`已迁移的行不会回滚。`). Both use the same reset route. |

### Repository backfill item (`repo-backfill`)

| ID | Contract |
|----|----------|
| B1 | The item is registered first (`order` 10) and requires downtime: a review that landed between a repoint and a soft delete would write against a target the batch just retired. |
| B2 | The worklist is the leftover shape — live targets whose `repo_id`, `repo_owner` and `repo_name` are all null — holding at least one ledger row, read in `id` order with the cursor `{ "last_target_id": string }`. A ledger row is any of `pull_requests`, `reviews`, `review_findings`, `review_failures` naming the target: sweeping a target's PRs does not sweep its reviews, so a PR-keyed worklist would strand the row. The scan is bounded like the work: at most 20 worklist rows are read per step. |
| B3 | Group identity is `(bot_id, owner, repo)` with owner/repo compared case-insensitively, because the uniqueness claim and the resolver are bot-scoped: two bots reviewing the same repository own two targets, while one bot's two workspaces own ONE. A step moves at most 20 groups, deduped case-insensitively, and every `IN (…)` list is chunked at 40 values. |
| B4 | Members are read for the whole bot — across its workspaces, not only the current batch: the winner is the row with the newest `pull_requests.last_seen_at` for that repository, then the newest `reviews.reviewed_at`, then the lowest id. Losers' configuration is discarded and counted in the batch log; no user choice is ever surfaced. |
| B5 | A group's home is the bot's live target that already names that repository, in any of the bot's workspaces, when one exists — adopting it keeps one live target per repository. Otherwise one new live target is inserted in the D22 winner's workspace, copying that winner's configuration with inheritance off (`follow_workspace_defaults = 0`). |
| B6 | The new target carries the repository's owner/name and no `repo_id`: identity is owner/name after the split, and the numeric id arrives with the repository's first delivery. The item never fabricates an id. |
| B7 | `pull_requests`, `reviews`, `review_findings` and `review_failures` are repointed from every member of the group onto the home target, matched by `(target_id, owner, repo)` case-insensitively, whichever workspace the member sits in. Two members holding the same PR number cannot both survive: the later `last_seen_at` (then the lower id) keeps the row and the duplicates are deleted before the repoint, so the unique key is never violated. |
| B8 | Only the batch's own old rows are retired, and only after every group of the batch ran — one row may hold ledger rows for several repositories, so retiring it inside a group would hide it from the next group. A member whose repositories did not all fit stays live and is read again by the next step, and the cursor never advances past a row left live. A later row whose only repositories were planned by an earlier row's groups is retired by the same batch: the worklist finds a row by any ledger row, so a row left live after they moved would never be scanned again. A row reads `done` only when the scan is short and nothing was left undrained. |
| B9 | A leftover row with no ledger rows is untouched except its inheritance flag (`follow_workspace_defaults = 0`), so its copied configuration keeps answering instead of the workspace's. It awaits its first delivery as a 待安装 row. |
| B10 | Preflight, with no writes: `unidentified_targets` (live rows of the leftover shape), `ledger_pairs` (the `(target, repository)` pairs a run moves), `conflicting_groups` (repositories covered by more than one live row) and `leftover_without_ledger` (rows of the leftover shape awaiting their first delivery). |
| B11 | Verify, read-only: `unidentified_targets_with_ledger` (a live row holding ledger rows but naming no repository) and `duplicate_repository_groups` (one bot naming the same repository twice among rows holding ledger rows, across its workspaces) must reach zero. Ledger rows still naming a retired target while a live target of the same bot already covers that repository are SPLIT by `run_started_at`: rows whose target was deleted at or after it are this run's crash residual and BLOCK (`unrepointed_ledger_rows` must reach zero); rows on a target deleted earlier are reported as the advisory `historical_rows` and never fail the item. With no `run_started_at` every such row is historical. "Holding ledger rows" means any of the four ledger tables throughout: `pull_requests`, `reviews`, `review_findings`, `review_failures`. A live named target with historical non-PR rows alone can therefore pass, an unidentified live leftover cannot pass until repointed, and no ledger row is deleted merely because its PR was swept. Also advisory, and exact: `ledger_rows_without_pr` counts ledger ROWS outside `pull_requests` (reviews, findings, failures) whose `(target_id, owner, repo)` has no matching PR row, owner/repo compared case-insensitively — three remaining non-PR rows read 3, for live or retired targets. It names no repair, so it never fails the item and never suppresses an overlapping blocking count. |
| B12 | Replay is idempotent: the worklist predicate is the leftover shape, and every row a batch creates or adopts names its repository, so a second pass over finished work moves nothing. |
| B13 | The item never attributes a ledger row whose `target_id` is null and never rewrites an adopted target's configuration. It deletes only the duplicate `pull_requests` rows that lose the merge; it does not delete reviews, findings or failures. |

### Orphan ledger attribution item (`orphan-ledger-attribution`)

| ID | Contract |
|----|----------|
| O1 | The second item (`order` 20) requires no downtime. It groups rows with `target_id IS NULL` across `pull_requests`, `reviews`, `review_findings` and `review_failures` by case-insensitive `(owner, repo)`. A live delivery already writes with a target and is not in the worklist. |
| O2 | Bot candidates are collected for each row from its own `bot_id` and from `bot_installations` by `installation_id`, including removed mappings. Both sources count: if they disagree, neither takes precedence. Every row must supply evidence and the group must name exactly one distinct bot; a row with no evidence cannot borrow a sibling's bot. Only a group with no evidence in any row can fall back to the deployment's only bot, if `bot_workspaces` names exactly one distinct bot. Multiple candidates, missing row evidence without that fallback, or no workspace for the resolved bot leave the group unattributable. |
| O3 | The item adopts the bot's one live target naming the repository case-insensitively. More than one live match makes the group ambiguous and unattributable; no target wins a tie. If no target matches, the item creates one in the bot's current workspace, with `created_by` set to the `runBatch` actor (`actor` stays an optional parameter only for call trees that predate it; the runner always supplies the operator login), `follow_workspace_defaults = 1` (the same UI-create rule as the alignment item and the add-repository path) and `repo_id` null for the first matching delivery carrying the numeric id to claim. It fills only null `target_id` values, never rewrites a non-null one, never deletes a row and never changes an existing target. |
| O4 | A step walks at most 20 groups in case-folded owner/name order, resuming after `{ "last_group": string }`. The cursor is a floor in the worklist read itself, so a batch aggregates only the groups it can still walk rather than re-reading the rows it already passed. It advances past unattributable groups without writing them. Preflight counts work but does not reserve targets: the batch transaction checks the live match, whether an insert can proceed and which workspace owns a new target. A matching target an operator adds after the worklist read is used rather than duplicated. The batch checks the remaining rows against the planned bot before writing. A group that no longer passes that check is left untouched; the batch log counts it under `changed_shape`, along with any other group planned for writes that had no ledger update. Target inserts and ledger updates commit together; a replay cannot pick up rows already attributed. The processed count is the ledger ROWS the batch moved (`0` on a replay); the batch log keeps the group count separately. |
| O5 | Preflight, with no writes: `orphan_rows` (all ledger rows with no target), `groups` (distinct repositories), `groups_with_target` (attributable groups with one live match), `groups_needing_target` (attributable groups with no live match), `unattributable_groups` (groups with no resolved bot or workspace, or with multiple live matches) and `ambiguous_groups` (groups with multiple live matching targets for the resolved bot). |
| O6 | Verify, read-only: `unattributed_ledger_rows` counts remaining null-target rows in attributable groups and must reach zero. `unattributable_groups` is advisory: those groups stay untouched and do not block completion. A completed item takes no further batch and its card has no reset control. To pick up groups that resolve after a repair, the card's impact text directs the operator to call `POST /_internal_admin/api/data-upgrades/orphan-ledger-attribution/reset` and then start the item again. |

### Ledger target alignment item (`ledger-target-alignment`)

| ID | Contract |
|----|----------|
| L1 | The third item (`order` 21) requires no downtime. It groups rows whose LIVE target names another repository than the row does, across `pull_requests`, `reviews`, `review_findings` and `review_failures`, by case-insensitive `(owner, repo)`. A row with a null target and a row whose target names no repository are both outside the worklist: `orphan-ledger-attribution` and `repo-backfill` own those shapes and run first. A live delivery already writes the target its repository resolves to and cannot enter the worklist. |
| L2 | The bot comes from the row's current target: a mismatched row always has one, and it names the tenant the row is visible in today, so aligning it never moves the row into a workspace that did not already count it. Rows of one group whose targets name different bots are disagreement, not a tie: the group is unattributable and left alone. One known bot and more than one live target naming the repository is ambiguity: the group is left alone and counted, and no target wins a tie. |
| L3 | The group's home is its bot's one live target naming the repository case-insensitively. When none exists the item creates one in that bot's current workspace with `created_by` set to the `runBatch` actor, `follow_workspace_defaults = 1` (the same UI-create rule as the add-repository path, so a repository the item creates inherits the workspace's review answers rather than being opted out of them) and `repo_id` null, and `review_targets`' own unique claim is never invented: `insert` and `update` both re-read the live match inside the transaction, so a target an operator adds after the worklist read is adopted rather than duplicated. Every `UPDATE` also re-tests the mismatch, so a row another writer just aligned is not rewritten. |
| L4 | Binding. When the target's `repo_id` is null and the repository's owner still has a LIVE `bot_installations` row for that bot (`account_login` case-insensitive), the item claims the id from GitHub: mint an installation token, `GET /installation/repositories`, match `full_name` to `owner/repo`, and write the id. Listings are cached per `installation_id` for the batch — one call per installation, never per group — and the calls run after the batch transaction commits, so no network call holds the write lock. A removed installation, a repository the installation does not grant, or any GitHub failure (no key, an undecryptable PEM, a rejected mint, an unreadable listing) leaves `repo_id` null, is counted in the batch log (`unbound`, `binding_failed`) and never fails the item: the repository's first delivery still claims the id (D15). |
| L5 | A step walks at most 20 groups in case-folded owner/name order, resuming after `{ "last_group": string }`, with the cursor floor pushed into the worklist read. `processed` is the ledger rows the batch moved and `log.aligned` the groups, the unit the walk pages in. The batch log also counts `created`, `bound`, `unbound`, `binding_failed`, `ambiguous` and `unattributable`. |
| L6 | Preflight, with no writes: `misaligned_rows`, `groups`, `groups_with_target` (actionable groups with one live match), `groups_needing_target` (actionable groups with no live match), `unattributable_groups` (rows whose targets name different bots, or no workspace to create a target in), `ambiguous_groups` (more than one live match) and `unbound_groups` (actionable groups whose target cannot be bound because the owner has no live installation). |
| L7 | Verify, read-only: `misaligned_ledger_rows` counts remaining rows in actionable groups and must reach zero. `ambiguous_groups`, `unattributable_groups` and `conflicting_ledger_rows` are advisory: those rows stay untouched and do not block completion, because no later pass could repair them — the operator resolves the duplicate target, merges the two PR rows, or fixes the bot mapping and re-runs. `conflicting_ledger_rows` counts `pull_requests` rows whose destination already holds that `(owner, repo, pr_number)`: `idx_pull_requests_target_pr` is unique over it, so a re-point would abort the whole batch, and choosing which copy survives is the operator's call. Replay is idempotent: the worklist predicate is the mismatch itself and every update re-tests it, so a second pass over aligned rows writes nothing and no ledger row is deleted. |

### Release-window coupling

| ID | Contract |
|----|----------|
| X1 | Migration `0068` installs the bot-level repository claim (`review_targets(bot_id, repo_id)` unique over live, identified rows). It is a schema migration, not an upgrade item: a live duplicate that predates it fails the deploy loudly instead of a winner being picked silently. |
| X2 | Migration `0069` creates `operator_data_upgrades` — the upgrade machinery's only new table. The maintenance keys need no migration: they live in the existing platform parameter store under its registered `platform.` domain. |
| X3 | Migration `0067` drops the allowlist and the installation binding, and no upgrade item exists for the allowlist: its rows are deleted with the table and migrate nowhere. The upgrade items move repository identity and repoint or attribute historical ledger rows. |
| X4 | The surface and the backfill ship in one release window and the backfill runs after it: until the item completes, historical rows stay 待安装 and are claimed by their first delivery, so no repository goes unreviewed while the operator decides when to run it. |

| Surface | workspace member / owner / admin | platform operator |
|---|---|---|

| `/healthz` | 200 | 200 |

## Invariants

- Idempotent replay: a second step over finished work processes nothing.
- A downtime item never steps while the window is closed; the runner closes only a window it opened.
- A run's start is stamped once by its first step and kept across reset — it is the item's lifetime boundary, so verify always dates the item's own retirements.
- Verify refuses `completed` on any non-zero blocking check; an advisory count is reported and never fails the item. Verify and preflight write nothing.
- Ledger rows are repointed or deleted, never orphaned, and no upgrade item rebuilds a parent table.
- Neither upgrade invents a numeric `repo_id`: a newly created target names the repository, and the resolver claims its numeric id from a matching delivery.

## Change obligations

A change to the maintenance keys, the gated or exempt surface list, the item interface, the state machine, the ownership rules or the merge rule updates this page in the same change. A new upgrade item is registered here when it ships, with its own worklist and verify contracts.
