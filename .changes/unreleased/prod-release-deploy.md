- **Release-gated production environment**: a **non-prerelease** release now deploys a second Worker, `mstar-inspector-production` at `https://inspector.mstar.page`, with its own D1, KV namespace, queue pair (`review-queue-prod` / `review-dlq-prod`) and container application; nothing is shared with the staging Worker `mstar-inspector` (`mstar-inspector.42ch.dev`), which keeps deploying on every push to `main`. The Release workflow starts that deploy by dispatching the production workflow on the tag — a Release published with the workflow's `GITHUB_TOKEN` triggers no `release: published` run, so the explicit dispatch is what starts the deploy for that Release, and the release job needs `actions: write` for it (a Release published by hand instead deploys through the retained `release: published` trigger, whose job-level tag guard skips a prerelease tag). The automated chain never dispatches a prerelease (`-` in the tag) to production; a manual `workflow_dispatch` on a tag ref **may** deploy one — that is how the first bring-up happens, and rollback dispatches the same way (`gh workflow run deploy-prod.yml --ref <tag>`). The production workflow takes no `ref` input, so a run deploys exactly the tag it runs on and the run's ref is the deployed checkout (a non-tag ref is refused before any mutation).
- **Release evidence names the production run**: each GitHub Release's *Deploy evidence* section now resolves the production deploy run for the tagged commit instead of the staging run.
- **Production bring-up documented**: `docs/deploy.md` gains a Production environment section (the two deploy paths, the one-time Cloudflare + GitHub `production` environment runbook — created **without** a branch policy, because a branch-only policy rejects tag-ref deployments — the extra OAuth callback URL, why `ADMIN_LOGINS` lives in `wrangler.jsonc` `env.production.vars`, the `env.production` duplication maintenance rule, and rollback), `docs/release.md` describes the production deploy, and `.env.example` states the environment scoping (shared repository variables, per-environment secrets).

- **发布门控的生产环境**：**非预发布**的 release 现在会部署第二个 Worker——`mstar-inspector-production`，服务地址 `https://inspector.mstar.page`——拥有独立的 D1、KV namespace、队列对（`review-queue-prod` / `review-dlq-prod`）与容器应用，与暂存 Worker `mstar-inspector`（`mstar-inspector.42ch.dev`）不共享任何资源；暂存环境仍随每次 `main` 推送部署。该部署由发布工作流在 tag 上**显式派发**生产工作流启动——用工作流自身 `GITHUB_TOKEN` 发布的 Release 不会触发 `release: published`，因此该 Release 的部署由这次显式派发启动，且发布 job 需要 `actions: write` 权限（由人工手动发布的 Release 则通过保留下来的 `release: published` 触发器部署，其 job 级 tag guard 会跳过预发布 tag）。自动化链路永不把预发布（tag 含 `-`）派发到生产；人工按 tag ref 执行 `workflow_dispatch` 则**可以**部署预发布——首次上线正是如此，回滚也按同样方式派发（`gh workflow run deploy-prod.yml --ref <tag>`）。生产工作流不接受 `ref` input，因此运行所跑的 tag 就是它部署的 tag，运行 ref 即实际部署的检出（非 tag ref 会在任何变更前被拒绝）。
- **发布证据指向生产运行**：每个 GitHub Release 的 *Deploy evidence* 区块改为解析该 tag 对应的生产部署运行，而不再是暂存运行。
- **生产环境上线文档**：`docs/deploy.md` 新增「Production environment」章节（两条部署路径、一次性 Cloudflare + GitHub `production` environment 手册——创建时**不加** branch policy，因为仅分支策略会拒绝 tag ref 部署——额外 OAuth 回调地址、`ADMIN_LOGINS` 为何写在 `wrangler.jsonc` 的 `env.production.vars`、`env.production` 重复维护规则，以及回滚方式），`docs/release.md` 描述生产部署，`.env.example` 说明环境作用域（仓库变量共享、secret 按环境设置）。
