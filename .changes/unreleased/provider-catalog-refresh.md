- **The provider catalog now refreshes itself daily, behind one reviewed PR**: a scheduled workflow (`refresh-catalog.yml`, 04:17 UTC) re-fetches the models.dev directory through `scripts/provider-catalog/fetch-models-dev.ts` — which converts the upstream id-keyed `models` map into the trimmed snapshot the generator reads, writes nothing when the payload is byte-identical to the committed one, and prunes older dated snapshots — then regenerates both contract modules. The generator no longer carries a hardcoded snapshot date: it reads the newest dated snapshot, so a refresh is a data commit rather than a code edit. When the omp SDK or harness engine has a newer release, the same run moves every pin surface (both manifests, `HARNESS_VERSION`/`harnessRef`, the CLI pin and the Dockerfile) and notes it in the PR. The PR lands on the fixed branch `chore/catalog-refresh`, opens once and is updated in place afterwards, and the body lists every provider and every model id the regeneration removed — a chain naming a vanished id fails at request time, so that list is the review's reason to exist. Red checks still publish the PR, labelled `⚠ tests red`; nothing auto-merges and nothing pushes to `main`.

- **provider catalog 现在每日自动刷新，并收敛为单个待审 PR**：新的定时工作流（`refresh-catalog.yml`，UTC 04:17）经 `scripts/provider-catalog/fetch-models-dev.ts` 重新抓取 models.dev 目录——该脚本把上游按 id 索引的 `models` 映射转换成生成器读取的裁剪快照，与已提交快照字节一致时不写任何文件，并清理更旧的日期快照——然后重新生成两个契约模块。生成器不再硬编码快照日期，改为读取最新的日期快照，因此刷新是一次纯数据提交而非代码修改。当 omp SDK 或 harness engine 有新版本时，同一次运行会同步全部 pin 面（两个 manifest、`HARNESS_VERSION`/`harnessRef`、CLI pin 与 Dockerfile），并在 PR 中说明。PR 固定落在 `chore/catalog-refresh` 分支，首次创建、后续就地更新；正文列出本次重新生成删除的全部 provider 与模型 id——引用已消失 id 的 chain 会在请求时失败，因此这份清单正是评审需要它的原因。检查为红时仍会发布 PR，并标注 `⚠ tests red`；不会自动合并，也不会推送到 `main`。
