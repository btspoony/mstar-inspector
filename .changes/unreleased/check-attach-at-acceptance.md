- **The review Check attaches when the delivery is accepted, and closes right after the verdict.** The Check attempt is now claimed and its `in_progress` run created on the delivery path — the same webhook request that answered `accepted` and enqueued the job — instead of inside the consumer's admission block, so the attach no longer waits for the queue and a cold sandbox. The admitted message adopts that released row through the same fenced claim (epoch bump, execution deadline narrowed to the 900 s execution window) and terminalizes the run inline from its handle. Measured on staging before this change: attach lag was the queue delay — 10 s, 3 m 20 s, 16 m 45 s and 15 m 31 s across four pull requests — and post-verdict close took 122 s and 113 s, because 69 of 85 attempts in seven days recorded `terminalize_outcome = 'no-handle'`: the consumer never held a handle, so its step-12 terminalize could never run. The attach is best-effort on the invocation context — a Check failure changes neither the `accepted` answer nor the enqueue, and every failure is one structured warn — and a duplicate delivery, a queue redelivery or a synchronize event for the same head still creates no second run. A row nobody ever adopts is closed by the Check reconciler when the attach window (one hour) expires, with the existing `expired` conclusion.

- **审查 Check 在投递被接受时挂载，并在给出结论后立即收口。** Check 尝试现在在投递路径上认领并创建 `in_progress` 运行——与回答 `accepted` 并完成入队的是同一次 webhook 请求——而不再位于消费方的准入块内，因此挂载不再等待队列与冷启动沙箱。被准入的消息通过同一套带围栏的认领接管这条已释放的行（epoch 递增，执行截止收窄为 900 秒执行窗口），并用自己的 handle 就地收口该运行。改动前的预发环境实测：挂载延迟等于排队延迟——四个 PR 分别为 10 秒、3 分 20 秒、16 分 45 秒与 15 分 31 秒；给出结论后的收口耗时 122 秒与 113 秒，因为七天里 85 次尝试中有 69 次记录为 `terminalize_outcome = 'no-handle'`：消费方从未持有 handle，其第 12 步的收口因此根本无法执行。挂载在调用上下文上尽力而为——Check 失败既不改变 `accepted` 应答也不影响入队，每次失败只产生一条结构化 warn——同一 head 的重复投递、队列重投或 synchronize 事件仍不会创建第二次运行。始终无人接管的行由 Check 协调器在挂载窗口（一小时）到期时以既有的 `expired` 结论关闭。
