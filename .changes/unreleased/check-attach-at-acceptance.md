- **The review Check attaches when the delivery is accepted, and closes right after the verdict.** The Check attempt is now claimed and its `in_progress` run created on the delivery path — before `REVIEW_QUEUE.send`, not inside the consumer's admission block — so the attach no longer waits for the queue and a cold sandbox, and an admitted message finds a released row instead of racing its creator. The webhook waits at most 2.5 s for the attach; past that the enqueue proceeds and the attach finishes on the invocation context. When the message is admitted before the attach released the row, the consumer retries the adoption once, 250 ms later, as long as the row is still under a delivery holder (never for a running review's holder or a frozen intent), and it takes over a delivery holder that has been silent for 5 s. A released attach row carries a two-minute grace due time, so if nobody adopts it the minute reconciler takes it then — not at the one-hour window's expiry. A delivery that is SKIPPED before execution — an idempotency hit, a publication-journal hand-off, a paused App — settles its attached run `neutral` with the skip reason instead of leaving it to close red at the one-hour window. The settlement follows the payload's head SHA (what the attach used, not the checkout) and does not retire the head: a retried or resumed delivery still claims a fresh generation and runs its own review. An in-flight guard rejection settles only on the final, terminal refusal (the retried refusals settle nothing, so a duplicate delivery can never close the live review's run); a retry that is later admitted still claims a fresh generation with its own run — a neutral settlement never retires the head. Where the App's Checks client is already at hand the skip sends that one update itself; on a paused App — whose gate makes zero credential/GitHub calls — the skip only freezes the intent, and the minute reconciler sends it on its next pass. The admitted message adopts the row through the same fenced claim (epoch bump, execution deadline narrowed to the 900 s execution window) and terminalizes the run inline from its handle; an adoption that lands after the begin budget releases the row again rather than returning a handle nobody awaits. Measured on staging before this change: attach lag was the queue delay — 10 s, 3 m 20 s, 16 m 45 s and 15 m 31 s across four pull requests — and post-verdict close took 122 s and 113 s, because 69 of 85 attempts in seven days recorded `terminalize_outcome = 'no-handle'`: the consumer never held a handle, so its step-12 terminalize could never run. A refused attach (no Checks surface, a token/GitHub refusal, a failed run-id write) is one redacted `check_attach_failed` warn and changes neither the `accepted` answer nor the enqueue; a release fenced out by an adopting consumer is not a failure. A duplicate delivery, a queue redelivery or a synchronize event for the same head still creates no second run.

- **审查 Check 在投递被接受时挂载，并在给出结论后立即收口。** Check 尝试现在在投递路径上认领并创建 `in_progress` 运行——在 `REVIEW_QUEUE.send` 之前，而不是位于消费方的准入块内——因此挂载不再等待队列与冷启动沙箱，被准入的消息也会找到一条已释放的行，而不是与创建者抢跑。webhook 最多等待挂载 2.5 秒；超过后照常入队，挂载在调用上下文上继续完成。若消息在挂载释放该行之前就被准入，消费方会在 250 毫秒后重试一次接管（仅当该行仍由投递持有者持有；正在运行的审查持有者与已冻结意图绝不重试），并可接管已静默 5 秒的投递持有者。已释放的挂载行带有两分钟的宽限到期时间，因此若无人接管，每分钟的协调器会在那时接手——而不是等到一小时窗口到期。在执行前就被跳过的投递——幂等命中、发布日志交接、App 暂停——会把已挂载的运行以 `neutral` 结清并写明跳过原因，而不是让它在一小时窗口到期时变红。结清按载荷的 head SHA（即挂载所用的提交，而非检出的提交）定位，并且不会让该 head 退役：被重试或恢复的投递仍会认领新的 generation 并运行自己的审查。并发守卫拒绝只在最后一次（终态）拒绝时结清（并写明拒绝原因；前三次重试不结清，因此重复投递绝不会关掉正在运行的那次审查的运行），而之后被准入的重试仍会认领新的 generation 并获得自己的运行——neutral 结清不会让 head 退役。若该 App 的 Checks 客户端已经就绪，跳过路径会自己发送这一次更新；对已暂停的 App（其门禁要求零凭据/零 GitHub 调用），跳过路径只冻结意图，由每分钟的协调器在下一轮发送。被准入的消息通过同一套带围栏的认领接管该行（epoch 递增，执行截止收窄为 900 秒执行窗口），并用自己的 handle 就地收口该运行；若接管发生在 begin 预算耗尽之后，则把行重新释放，而不是把一个无人等待的 handle 返回出去。改动前的预发环境实测：挂载延迟等于排队延迟——四个 PR 分别为 10 秒、3 分 20 秒、16 分 45 秒与 15 分 31 秒；给出结论后的收口耗时 122 秒与 113 秒，因为七天里 85 次尝试中有 69 次记录为 `terminalize_outcome = 'no-handle'`：消费方从未持有 handle，其第 12 步的收口因此根本无法执行。被拒绝的挂载（没有 Checks 面、token/GitHub 拒绝、run id 写入失败）只产生一条经脱敏的 `check_attach_failed` warn，既不改变 `accepted` 应答也不影响入队；被接管方抢先完成的释放不算失败。同一 head 的重复投递、队列重投或 synchronize 事件仍不会创建第二次运行。
